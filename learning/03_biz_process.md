# テーマ3：業務設計

> 学習週：Week 2（前半）、Week 3（後半）  
> 優先度：★1位（DXの本体はここにある）

---

## なぜこれを学ぶか

DXの本体は道具の導入ではなく**業務設計の再構成**。  
どんなシステムも、業務設計が間違っていれば役に立たない。  
「ITを入れたが何も変わらない」の根本原因は業務設計の失敗。

---

## 1. 業務設計の基本要素

```
業務設計 = 以下を明確に定義すること

① 誰が（役割・担当）
② 何をトリガーに（開始条件）
③ 何を（アクション・判断）
④ 何を使って（情報・ツール）
⑤ 誰に（渡し先・通知先）
⑥ どのような状態で（完了条件）
⑦ 何を記録するか（証跡）
```

---

## 2. 業務フローの設計

### 2.1 基本ステップ
1. **現状の業務を書き出す（AS-IS）**：実際にどうやっているかを観察で記録
2. **ムダ・問題点を特定する**：待ち・重複・不明確な判断・属人化
3. **あるべき姿を設計する（TO-BE）**：目的から逆算した理想の流れ
4. **移行計画を作る**：AS-IS → TO-BE への移行手順

### 2.2 判断点の設計

業務フローの中で**誰が・何を基準に・何を判断するか**を明確にする。

```
良い判断点の設計：
  ・判断基準が数値や状態で定義されている（曖昧でない）
  ・判断者の役職・権限が明記されている
  ・判断に必要な情報が整っている状態が定義されている
  ・判断結果（承認/却下/差し戻し）ごとの次のステップが定義されている

悪い判断点の例：
  「適切に判断する」→ 誰が何を基準に判断するのか不明
  「上長に確認する」→ どの上長か、何を確認するのかが不明
```

### 2.3 BPMN記法（業務フロー図の標準）

```
○ ：イベント（開始・終了・エラー発生など）
□ ：タスク（具体的な作業）
◇ ：ゲートウェイ（条件分岐・並行処理）
─→：シーケンスフロー
点線：メッセージフロー（部門間の情報授受）
水泳レーン：担当者・部門の区分け
```

## 3. 責任分担の設計

### 3.1 RACI マトリクス

| 記号 | 意味 |
|------|------|
| **R（Responsible）** | 実行責任：実際に作業をする人 |
| **A（Accountable）** | 説明責任：最終判断・承認をする人 |
| **C（Consulted）** | 相談される：作業前に意見を求める人 |
| **I（Informed）** | 情報共有される：結果を知らせる人 |

```
設計変更承認の例：

              設計担当 | 製造担当 | 品質担当 | 部門長
変更要求の作成    R    |    I    |    C    |   I
影響範囲調査      C    |    R    |    R    |   I
技術的承認        A    |    C    |    R    |   I
最終承認          I    |    I    |    I    |   A
展開・指示        I    |    R    |    C    |   I
```

## 4. 属人化を防ぐ設計

### 4.1 属人化の原因

```
①知識が頭の中だけにある（文書化されていない）
②手順が人によって違う（標準化されていない）
③判断基準が個人の感覚に依存している
④情報が特定の人にしか届かない設計になっている
⑤引継ぎの仕組みがない
```

### 4.2 対策の設計原則

| 問題 | 対策 |
|------|------|
| 暗黙知がある | 手順書・判断基準の文書化 |
| 人によって手順が違う | 標準作業手順（SOP）の整備と遵守確認 |
| 担当者が休むと止まる | バックアップ担当者の指定と訓練 |
| 情報が属人的に管理される | 情報の一元管理・共有フォルダ・システム化 |
| 引継ぎが不完全 | 引継ぎチェックリストの整備 |

## 5. 二重入力・手戻りを防ぐ設計

### 5.1 二重入力が起きる原因

```
システムAに入力 → システムBにも同じ内容を入力
        ↓
誤記・転記ミス・工数ムダ・データ不整合
```

### 5.2 設計原則：Single Source of Truth（唯一の正）

```
情報は1か所でのみ入力・管理する
他のシステムはその情報を参照・連携する

例：品番の入力はPLMのみ → ERP・MESはPLMから取得
   顧客情報の入力はERPのみ → MES・QMSはERPから取得
```

### 5.3 手戻りが起きる原因と対策

```
原因：
  前工程の情報が不完全なまま次工程に進む
  設計情報と製造情報が分断されている
  承認前に作業が始まる

対策：
  次工程への受渡し条件（Gate条件）を定義する
  Gate条件を満たさない情報は次工程に渡さない
  情報の完結性チェックをプロセスに組み込む
```

---

## 6. 設計→製造→品質→保全を分断しない

```
分断が起きると：
  設計変更が製造に届かない
  製造での不具合が設計にフィードバックされない
  品質問題の根本原因が設計にあっても製造で対処している
  保全の問題が品質に影響していても気づかない

分断しないための設計：
  ①情報の流れを明示的に設計する（誰から誰へ・何の情報を・いつ）
  ②各工程間の受渡し条件を定義する
  ③問題が下流で発生したとき上流に遡るルートを設計する
```
