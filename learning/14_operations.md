# テーマ14：運用設計

> 学習週：Week 15  
> 優先度：統合（作っただけでは価値は出ない）

---

## 1. 運用設計とは

```
「作った仕組みを使い続けられる設計」まで含めて初めて仕組みになる

運用設計が必要な理由：
  ① システムは時間とともに劣化する（データが古くなる・バグが出る）
  ② 業務は変化する（新製品・組織変更・規制改訂）
  ③ 担当者は変わる（引継ぎが必要）
  ④ 異常が起きる（対応手順が必要）
```

---

## 2. 定期運用のサイクル設計

### 2.1 日次・週次・月次の役割分担

```
日次（毎日）：
  □ システム正常稼働の確認
  □ 前日データの品質チェック（欠損・異常値）
  □ アラートへの対応

週次（毎週）：
  □ KPIダッシュボードの確認
  □ 未解決アラートのレビュー
  □ データ品質の傾向確認

月次（毎月）：
  □ KPI目標値との比較・分析
  □ マスターデータの棚卸し・更新
  □ ユーザーからのフィードバック収集
  □ 改善項目のリストアップ・優先順位付け
  □ システム・業務フローの見直し検討
```

## 3. 更新責任の設計

```
「誰が何を更新する責任を持つか」を事前に明確にする

更新対象           更新責任者      更新頻度
品番マスター       設計部門        都度（設計変更時）
工程マスター       製造部門        都度（工程変更時）
取引先マスター     購買部門        都度（新規取引先時）
設備マスター       保全部門        都度（設備追加・廃棄時）
KPI定義           管理部門        半年〜年1回
アクセス権限      システム管理    人事異動時
```

---

## 4. 異常時対応の設計

### 4.1 停止基準と再開基準

```
停止基準（システムを止める条件）：
  ・データ品質が一定以下に低下した場合
  ・誤判定率が閾値を超えた場合
  ・セキュリティインシデントが発生した場合

再開基準（システムを再開できる条件）：
  ・停止原因が特定・解決されたこと
  ・品質指標が基準値以上に回復したこと
  ・責任者の承認があること
```

### 4.2 代替手順（フォールバック）

```
システム停止時に業務を止めない手順：
  ① 紙の帳票によるバックアップ
  ② 別システムへの一時切替
  ③ 手順の簡略化（重要項目のみ記録）

代替手順の要件：
  ・担当者全員が知っている
  ・定期的に訓練している
  ・代替手順での記録を後でシステムに戻す方法がある
```

## 5. 保守体制の設計

```
運用に必要な役割：
  システム管理者：技術的な保守・更新
  業務管理者：業務ルール・マスターデータの管理
  ヘルプデスク：ユーザーからの問い合わせ対応
  ベンダー：障害対応・バージョンアップ

サポートレベル（SLA）の設計：
  Level 1（軽微）：翌営業日以内に対応
  Level 2（重要）：4時間以内に対応
  Level 3（緊急）：1時間以内に対応・24時間対応
```
